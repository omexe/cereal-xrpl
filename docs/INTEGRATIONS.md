# Ledger and Mastercard: how cereal integrates each, and what each judge is told to look for

Written Sat Oct 24 ~3 PM from the resources the organizers attached to the two partner filters (Ledger: xrplnyc page, XRP Signer reference, Ledger for Agents, Earn; Mastercard: Developers MCP, Agent Pay, AP4M release, a slide deck), the signer and device-app source code, t54's facilitator docs, and the Verifiable Intent spec. Verbatim quotes are the sponsors' own words.

## 1. Ledger ($3,000 Agentic Finance; $4,000 Protocol Innovation is a different build)

### What they wrote
- Requirement: "your project must land at least one transaction on the XRP Ledger or its EVM sidechain. Testnet counts."
- Agentic Finance: "device-backed security is central: agents that pay for tools and services, human-in-the-loop approval for sensitive actions… Agents that use secrets they cannot leak: a broker hands out scoped capabilities, never the API key… Agents that settle on XRPL: streaming payments, per-call micropayments, or escrow-backed work agreements, all approved on device."
- The bar for every track: "Ledger used as a real trust layer, not just wallet branding. Signs on a real device against testnet or the EVM sidechain. Fills a real gap rather than rebuilding something that already exists. A working demo we can run, not a slide deck. Clear boundaries between what is automated and what a human approves. Reusable by other developers where it makes sense: a library beats a one-off."
- "We judge the Developer Experience (DX) feedback as much as the code."
- Ledger's own budget doctrine (Agent Intent docs, Ethereum/Solana only today): "You approve the budget, not every payment… The agent can only spend what you approve, and it cannot refill its own wallet."

### What the device can do (verified in source, not in the docs)
- `@ledgerhq/device-signer-kit-xrp` is a byte signer: `signTransaction(path, Uint8Array)`. Pass plain `encode(tx)`; the device app adds the signing prefix itself. **If the top-level `SigningPubKey` is empty, the app uses the multisign prefix and appends its own AccountID**, i.e. the device produces a valid multisig `Signer` for any account whose signer list includes the device's address. Parallel multisign only: never pass a transaction that already carries `Signers`.
- Clear-signed on device: Payment (XRP and issued currencies, so RLUSD), TrustSet, SignerListSet, AccountSet, **AccountDelete**, SetRegularKey, Escrow, PaymentChannel, Offers, Checks, AMM, NFToken, Clawback, DepositPreauth, Tickets.
- Blind-signing only: Credential*, PermissionedDomain*, MPToken*, Batch, DelegateSet, Vault*. (Our credential transactions are signed by cereal's software issuer key, so the device never meets them.)
- Agent Intent and the Wallet CLI do not support XRPL; Key Ring (secret encryption into a process) is chain-agnostic.

### The integration, in priority order
1. **The Ledger is the recovery key.** The burner's signer list becomes {agent 1, cereal 1, **owner's Ledger 2**}, quorum 2. Normal payments: agent + cereal. The device alone (weight 2) can sweep the remainder home and `AccountDelete` the burner, both clear-signed, without cereal's cooperation. The agent alone still gets `tefBAD_QUORUM`; cereal alone still cannot spend. Line: "If cereal disappears tonight, your Ledger takes your money back tomorrow morning. Nobody else can." This is "device-backed security central", "clear boundaries", and Protocol-track language ("multisig treasuries… no type-aware helpers") in one object. Implemented in `cereal/lock.py` (`recovery_addr`) and `ledger/multisign.ts`. **Verified on testnet Oct 24:** locked burner with {cereal 1, Ledger 2, agent 1}; device-only sweep `9A10502B…` tesSUCCESS; agent alone `tefBAD_QUORUM`; agent + cereal `7B2FC286…` tesSUCCESS.
2. **The Ledger approves every budget.** The treasury's RLUSD funding Payment is clear-signed on the device (`ledger/fund.ts`, same fields as `cereal/fund.py`). "Approve the budget, not every payment" is their sentence; the burner "cannot refill its own wallet" is our lock.
3. **Agent Intent for XRPL, in their vocabulary.** Fund, top-up and burn are intents the agent proposes and the owner approves on device; routine x402 calls draw from the approved budget without a prompt. Say plainly that Ledger Agent Intent is Ethereum and Solana only today and that cereal is the XRPL shape of it, built on DMK.
4. **A library, not a one-off.** Package `ledger/multisign.ts` as `ledger-xrpl-multisign` (device → `Signer` entry, combine, submit) and `ledger/fund.ts`. Their words: "a library beats a one-off"; the Protocol track asks for exactly "device-signed tooling for… multisig treasuries".
5. **DX feedback as a deliverable** (`docs/DX-FEEDBACK.md`, screenshots): the signer reference still documents `Signature = { r, s, v }` while 0.3.0 returns a `Uint8Array` and takes a `curve` option; derivation-path examples are inconsistent (`44'/144'/0'/0/0` vs `m/44'/0'/0'/0/0`); nothing on the portal says the device adds the signing prefix or how to multisign (it is only in the app-xrp README); the blind-signing requirement for Credentials/Batch/DelegateSet is undocumented; a `multisign` helper is the obvious missing API. File as issues or a PR on `device-sdk-ts`.
6. Optional if time: Key Ring (`wallet-cli ring encrypt/decrypt`) for vendor API keys the agent uses, as the literal "secrets they cannot leak".

Not possible today, say so if asked: Agent Intent on XRPL; XRPL Clear Signing metadata (no ERC-7730 equivalent); the device cannot sign the P-256 Verifiable Intent JWTs (XRPL signing only).

## 2. Mastercard ($6,000)

### What they wrote and what we know about the judging
- The opt-in form is titled "XRPL Hackathon 2026 - Mastercard AP4M Registration Form" / "Agentic Track Registration Form" and asks for team name, contact email and a wallet address "to receive testnet funding". The bounty is judged by AP4M people (Amol Sharma, confirmed judge: "secure, high-frequency microtransactions"; AP4M engineers Ao Li and Katie Li mentor).
- AP4M's four capabilities, verbatim: "Credentialing: Every agent is credentialed, and with Verifiable Intent, can be recognized and transact with trust across ecosystems. Permissioning: Organizations can set authorization rules and spending limits that are programmatically enforced… Transacting: Verified participants can connect and transact across providers and systems, enabling continuous, high-frequency automated commerce. Settling: Supports reliable, guaranteed multi-rail settlement across cards, accounts and stablecoins." Partners include Ripple and t54. RippleX in the same release: agents "can only ever do what they are authorized to do."
- Agent Pay: "Know your agent — Only registered agents can transact"; "Verifiable intent — every transaction is verified by authenticated user intent and explicit consent before an action is taken."
- **The hackathon slide deck is behind a Google sign-in (401 on export). Someone on the team should open it signed in and export it to PDF or text; it is the only place their rubric may be written down.**

### The integration, in priority order
1. **Attach a Verifiable Intent chain to every cereal x402 payment, through t54.** t54's XRPL facilitator already accepts a "Mastercard-aligned Verifiable Intent (VI) L1→L3 chain" inside the x402 `PAYMENT-SIGNATURE` header and runs it through Trustline's risk service (allow / deny / review gates settlement). With `x402-xrpl`: `RemoteIssuerProvider(issuer, issueRequest, ownerPrivateJwk, agentPrivateJwk, constraints)` passed as `verifiableIntentProvider` to the purchase; subject `did:pkh:xrpl:<burner>`, `allowedChains ["xrpl"]`, `allowedAssets ["RLUSD"]`, `spendingCeiling` = the job budget, `per_transaction_max` = the per-call cap. Issuer secret from portal.t54.ai (ask Frank He). This is AP4M's "credentialed… with Verifiable Intent" and "spending limits programmatically enforced", in the standard Mastercard maintains, settled in RLUSD. **Verify first (step 6) that the facilitator accepts a multi-signed Payment blob from the burner; if not, pay from a single-key spend wallet that the 2-of-2 burner tops up per call, and say so.**
2. **The conditions card is a Verifiable Intent L2 mandate.** The spec's L2 Autonomous layer is "constraints + agent key binding" (`mandate.payment.allowed_payees`, `mandate.payment.amount_range`, agent `cnf.jwk`, optional `prompt_summary`). cereal's compiled card already has those fields; render the card with the VI layer names and keep the owner's sentence as `prompt_summary`. Each co-signed payment is the L3 "final action". The accounting export is the "single, privacy-preserving record" of identity, intent and action they describe.
3. **Speak the four layers on the Mastercard table, each mapped to a ledger object.** Credentialing = XLS-70 vendor credential (+ VI L1 for the agent). Permissioning = 2-of-2 burner funded with the budget (+ L2 constraints). Transacting = x402 "exact" scheme via the t54 facilitator. Settling = RLUSD on XRPL. Their product verbs for the demo: Discover → Authorize → Execute → Settle. "Authorize once, transact many times, settle later" is their AP4M line; it is our burner.
4. **Use the Mastercard Developers MCP during the build and say so.** `claude mcp add --transport http mastercard-developers https://developer.mcp.mastercard.com` (docs/spec discovery only; no live API calls). Design the vendor-intelligence oracle that issues and revokes `cereal:vendor:*` credentials against the **MATCH Pro** spec Mastercard itself cites (the terminated-merchant list: "help acquirers identify potentially high-risk merchants") plus Merchant Identifier and Onboard Risk Check. Ship it as an adapter with a mock and a sandbox attempt; these products are acquirer-gated, so never claim live Mastercard data. The line for Amol Sharma: "cereal's vendor credential is MATCH for agent vendors, on a public ledger."
5. **Ask for the AP4M early-access sandbox on site.** The June release has no developer link ("contact your Mastercard representative"); early access opened Oct 20 with buyer and seller APIs and an x402 voucher model ("a secure promise to pay within its approved limit"). The form's funded wallet is the hook; Ao Li and Katie Li are the people. If access arrives, one AP4M voucher settled from a cereal burner is the headline; if not, the VI chain through t54 (an AP4M partner) is the honest equivalent.

Not possible today, say so if asked: registering an agent with Mastercard Agent Pay or getting network tokens for an XRPL wallet; Mastercard's own Verifiable Intent APIs ("available soon"); calling MATCH or merchant APIs through the MCP.

## 4. What changes in the build
- `cereal/lock.py`: signer list {agent 1, cereal 1, recovery 2} when `LEDGER_ADDRESS` is set (the device address from `ledger/` getAddress; Speculos today).
- `ledger/multisign.ts`: device signs a transaction as a multisig signer (empty `SigningPubKey`, no `Signers`), returns the `Signer` entry, combines, submits. Used for the recovery sweep and the burn.
- Step 6 gains the VI chain via `x402-xrpl`'s `RemoteIssuerProvider` once the facilitator accepts the burner's multi-signed blob.
- The demo gains one beat: "cereal goes dark; the owner's Ledger sweeps the burner alone."
